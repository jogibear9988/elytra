## Native graph

The headless probe uses the real LibWebView application, LibWeb/LibJS, Compositor,
RequestServer and separate WebContent OS processes. The owned WebContent entry
reuses upstream bootstrap and RendererSandboxLinux.cpp, with the existing
isolated-world/callback adapters. It does not substitute Node/V8, a WebView or
a VM/container runtime for Linux. Ladybird source stays unmodified at its pin.

The Linux development layout is:

```text
build/linux-renderer/
  bin/firefly-renderer-probe       upstream helper control
  bin/firefly-preload-probe        owned helper frontend
  bin/firefly-window-probe         native Qt view (not the Firefly desktop API)
  firefly-helper/
    bin/WebContent                actual owned ELF executable
    bin/RequestServer, ...         development symlinks to real upstream helpers
    share/Lagom/                  physical resource files
```

LibWeb's Linux resource-prefix convention is bin plus share/Lagom. The helper
links the native Linux sandbox source and upstream sanitizer helper source;
there is no fallback to RendererSandboxUnimplemented or disable-sandbox flag.
This is a development layout, not a relocatable distributable package.

## Toolchain and dependencies

The [Linux environment action](../../.github/actions/linux-environment/action.yml)
supplies the same pinned Clang 22, CMake 4.2.0 and Rust 1.98.0 environment as Mite,
plus native graphics/window-system headers and fonts for renderer builds.

Ladybird requires Qt 6.10 or newer. The owned Linux manifest generated by
tooling/renderer_dependencies.py adds Linux Qtbase/Positioning from Ladybird's
existing 6.11.2 overrides and baseline. It preserves original dependencies and
licenses, resolves overlay paths absolutely and refuses stale generated data.
It does not add Mite's I/O dependencies to the standalone renderer graph. Qt is
built through pinned vcpkg; the adapter does not rely on an older distribution Qt.

The pinned Linux Qt UI also requires Qtbase's wayland feature: its external-URL
activation source uses QWaylandApplication and private QWaylandWindow interfaces
while compiling the companion browser/resource target, even for X11/headless
acceptance. Include this feature with the existing X11 features and install the
native Wayland development/protocol prerequisites. Do not patch the upstream
activation code or omit its native compile gate to hide a mismatched Qt SDK.

Both the full frontend adapter and independent service project inspect the actual
imported Qt GUI SDK's enabled public features at configuration. A provider without
wayland fails before the large native compilation. This is an SDK feature-contract
check, not proof of native Wayland presentation/activation behavior; those tests
remain separate and unverified. Current native window/clipboard gates use xcb.


On a prepared native Linux machine:

```sh
python3 tooling/bootstrap.py
CC=clang-22 CXX=clang++-22 LDFLAGS=-fuse-ld=/usr/bin/ld.lld-22 \
  python3 tooling/build_renderer.py --build-dir build/linux-renderer --target firefly-preload-probe --jobs 3
cmake --build build/linux-renderer --target firefly-renderer-probe firefly-isolation-probe firefly-wire-process-probe --parallel 3
python3 tooling/renderer_dependencies.py --check build/linux-renderer/renderer-manifest
```

## Acceptance gates

The [native renderer workflow](../../.github/workflows/linux-renderer.yml) compiles
actual Linux executables, then requires:

- DOM/text execution, absence of privileged Mite capabilities, a real compositor
  PNG and separate WebContent/RequestServer/Compositor process identities;
- native realm isolation and cross-process serialized-data tests;
- the owned helper's first-script preload, lifetime/callback/revocation tests;
- QtCore-only clipboard wire preparation before the large renderer compilation;
- kernel sandbox observations for both the upstream control and owned helper;
- an actual Qt X11 window under Xvfb/Openbox: mouse/key delivery into LibWeb,
  viewport resize, navigation/close, painted screenshot colors and reported
  failure when the observed WebContent process is killed.

The process harness records the actual renderer PID and verifies its parent.
Linux acceptance reads /proc/PID/status while that process is alive: NoNewPrivs
must be 1, Seccomp must be filter mode 2 and Seccomp_filters must exceed the
parent frontend's filter count. It therefore does not count only an inherited
runner filter as renderer sandbox activation. Missing kernel evidence fails;
it is not silently skipped. These fields are described in the
[Linux process-status manual](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html).

This observes activation, not complete sandbox containment. Landlock/filesystem,
network/process broker policies, adversarial escapes and real desktop GPU/input
need further acceptance. A passing screenshot does not establish native windows.
CI retains logs, images, dependency manifests and CMake/vcpkg diagnostics on failure.
Software Mesa rendering is requested; sandbox settings are kept intact.

Clipboard wire preparation lives in firefly/native/clipboard/Protocol.cpp, shared
with the real macOS backend. Its standalone native probe validates owned byte
copies, item/representation shapes, supported MIME types, canonical Base64 and
aggregate limits without creating a window or accessing any OS clipboard. The
Linux workflow builds/runs that small target immediately after configuration.
This establishes parser portability only. The experimental X11 provider below
needs its own native process gate; public Linux Firefly integration remains unfinished.

Local macOS validation covers the same CMake layout selection and unchanged helper/
Firefly compilation. CMake/manifest adapter tests do not prove Linux compilation
or execution. Linux source/backend failures remain visible until the dedicated
hosted gates actually pass. Windows helper layouts/runtime still refuse explicitly.
The experimental Linux application target below now has native wiring; its actual
end-to-end runtime acceptance remains pending.

## Native X11 window probe

```sh
python3 tooling/build_renderer.py --build-dir build/linux-renderer --target firefly-window-probe --jobs 3
QT_QPA_PLATFORM=xcb python3 tooling/tests/test_window.py --probe build/linux-renderer/bin/firefly-window-probe
```

Run this on a Linux X11 desktop or under the workflow's Xvfb/Openbox session.
The gate requires the actual xcb Qt platform; offscreen/minimal backends cannot
pass. Xvfb is an X server on the native Linux runner, not a replacement runtime.
The test injects toolkit events, not physical keyboard/mouse input. Page-owned
pink/teal swatches are checked in the native window image using brightness and
contrasting channel differences. This tolerates display-profile transforms while
rejecting blank/neutral/monochrome captures; a PNG header alone cannot pass.

The owned Qt target uses upstream accessibility, X11 window hints and native
window-container sources. With upstream Vulkan DMA-BUF support enabled, it uses
the actual WebContentViewLinux implementation and depends on upstream's shader
generator outputs. It does not copy shaders, link the tabbed browser application,
or advertise Wayland/GPU-driver/physical-display acceptance. macOS AppKit probes,
presentation sources and the full desktop-runtime wiring live in separate CMake
modules. Linux desktop OS services and application packaging still need work.

## Static FFmpeg ELF link adapter

The first native x64 build reached LibMediaCodecs but failed on FFmpeg assembly
R_X86_64_PC32 references to preemptible ff_tx_tab_* data. The owned
firefly/renderer/LinuxFFmpeg.cmake module hides only the bundled static
libavcodec-ladybird, libavutil-ladybird and libswresample-ladybird archive symbols
from that component's ELF exports. Public LibMediaCodecs symbols remain exported;
upstream's separate dlopen/dlsym system-FFmpeg provider remains unchanged.
This avoids changing Ladybird/FFmpeg source or disabling media/assembly features.

Before the large graph, the Linux x64 workflow runs an actual ELF regression:
the unadapted PC-relative archive link must fail, the adapted shared-library link
must succeed, its public API must execute and readelf must confirm that private
archive symbols are absent from dynamic exports. This fixture is not FFmpeg
media-decoding acceptance. Full native renderer linkage/execution remains pending
until the real dependency graph passes the subsequent gates.

## Native X11 clipboard service

Status: experimental native component; **isolated Linux X11 acceptance passed**
for f05a24b in [run 42299888412](https://github.com/jogibear9988/elytra/actions/runs/42299888412),
job 128174620346. All three tests pass in 0.44 seconds, including the actual
independent cross-process X11 reader/writer pairs. The corrected Wayland-enabled
Qt 6.11.2 selection also builds and passes all three native-service tests in
0.29 seconds for 4b3a83d in
[run 42303495733](https://github.com/jogibear9988/elytra/actions/runs/42303495733),
job 128192217506. The actual imported SDK feature guard passes; this is X11
execution, not Wayland runtime or full renderer acceptance. The added geometry
gate still requires its separate native result.
The experimental Linux application target links this native backend; native X11
window geometry and the relocated public app fixture pass at `19ad113`. The existing macOS
runtime keeps its AppKit provider; standalone Mite still has no GUI dependency.

ClipboardX11.cpp implements the shared bounded protocol through QClipboard and
QMimeData on the native xcb application thread. Prepared text/plain, text/html
and text/rtf byte snapshots acquire X11 clipboard ownership only after validation.
Reads reject unknown content formats and changed providers instead of knowingly
returning a mixed/partial item. The X11 transfer targets TARGETS, MULTIPLE,
TIMESTAMP and SAVE_TARGETS are protocol metadata, not returned content. The pinned
Qt implementation canonicalizes STRING/UTF8_STRING/TEXT to text/plain.

The adapter requires a running native Qt GUI event loop. Under X11 the owner
serves selection requests and must stay alive; see the
[Qt clipboard documentation](https://doc.qt.io/qt-6/qclipboard.html).
There is no persisted clipboard guarantee after owner exit. External providers
may allocate/block during transfer; eight-MiB checks do not impose a total OS/
process memory cap. Qt can represent a failed transfer as empty data; complete
provider-error parity is not claimed. Wayland, PRIMARY selection and Windows
clipboard integration remain separate unfinished work.

The workflow builds firefly-x11-clipboard-probe immediately after configuration,
before the large LibWeb graph, and runs tooling/tests/test_x11_clipboard.py under
its own Xvfb server. The probe refuses before QGuiApplication construction unless
FIREFLY_TEST_ISOLATED_X11=1; the harness also requires Linux, DISPLAY and xcb.
Do not run it on your ordinary desktop: it intentionally replaces that X server's
clipboard. No such probe is run against the local macOS desktop.

Three actual owner/consumer pairs check an owned write with an independent Qt
reader, an independent Qt writer with owned reads, and unknown external content
refusal while plain text remains readable. Unicode, embedded NUL, HTML/RTF raw
bytes, MIME metadata, live ownership, invalid-write preservation and clear are
required. The independent roles bypass the Firefly wire/backend on their side.
Each owner runs its native event loop; the harness kills its process group and
waits for teardown. No offscreen backend, mocked clipboard or silent skip can
satisfy this native gate. Compile/guard acceptance on macOS is not Linux acceptance.

## Independent native-service CI

The [native OS-service workflow](../../.github/workflows/linux-services.yml) runs
independently of the serialized full renderer workflow. It configures
firefly/native as its own CMake project and builds only the owned Qt service
libraries/probes. No LibWeb, LibJS, Mite or renderer process is linked into these
small acceptance executables. It therefore provides OS-service feedback while
the separate full browser/renderer graph is still compiling.

The --services manifest mode retains the renderer's exact Linux Qtbase features,
upstream baseline/overrides and absolute overlays. It selects Qt as the standalone
service dependency instead of installing the whole browser graph; it does not
change the renderer manifest or vendor files. Generated manifest guards reject
using the service graph as the full renderer graph. Vcpkg checks dependency ABIs;
matching cache paths permit reuse of already compiled renderer Qt packages.

On a prepared native Linux machine, from the repository root:

```sh
python3 tooling/bootstrap.py
python3 tooling/renderer_dependencies.py --services --prepare build/linux-native-services/manifest
CC=clang-22 CXX=clang++-22 LDFLAGS=-fuse-ld=/usr/bin/ld.lld-22 \
  cmake -S firefly/native -B build/linux-native-services -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_TOOLCHAIN_FILE="$PWD/build/vcpkg/scripts/buildsystems/vcpkg.cmake" \
  -DVCPKG_MANIFEST_DIR="$PWD/build/linux-native-services/manifest"
cmake --build build/linux-native-services --parallel 3
FIREFLY_TEST_ISOLATED_X11=1 QT_QPA_PLATFORM=xcb xvfb-run -a \
  ctest --test-dir build/linux-native-services --output-on-failure
```

The native Linux project requires byte-protocol, isolation-guard and real
cross-process X11 acceptance. On macOS it only registers the four non-GUI tests;
that local compilation/guard coverage is explicitly not Linux OS acceptance.
The guard strips the test opt-in before launching the executable, requiring its
refusal before GUI initialization. CTest and subprocess deadlines bound failures.
Missing X11 prerequisites fail, rather than silently skipping the native test.
The complete renderer/window/sandbox/preload gates remain mandatory in their
own workflow; a passing isolated clipboard component does not certify Firefly
Linux app lifecycle, integration, packaging or security containment.

## Experimental Mite-driven X11 application

Status: **implemented integration candidate; native Linux compilation/execution
pending its hosted gate**. This extends the source/build path beyond renderer
probes. It does not certify Linux desktop support, Electron parity or packaging.

The actual firefly target embeds the same LibJS/Mite main process and common
BrowserWindow, preload, contextBridge and IPC implementation used by macOS. It
selects the native X11 clipboard and Linux geometry/centering adapters, plus the
actual upstream Linux renderer sandbox. No Node/V8/Electron runtime is substituted.
Display metadata and native theme preferences remain unavailable: native reads
throw ERR_FIREFLY_UNSUPPORTED_API. The themeSource getter and setters also refuse,
including assigning the existing default; no guessed display IDs/preferences or
empty successful values are provided. Standalone Mite keeps its separate graph.

Native services are selected through one platform binding seam. macOS retains
its AppKit/CoreGraphics implementations and owner-scoped notification teardown.
The Linux startup guard requires explicit QT_QPA_PLATFORM=xcb and a nonempty
DISPLAY before GUI construction; Wayland and missing-display startup refuse.
firefly --help remains available without a display.

On a prepared native Linux machine, with the pinned compiler/dependencies:

```sh
python3 tooling/build_renderer.py --build-dir build/linux-renderer \
  --target firefly --ccache --jobs 3
QT_QPA_PLATFORM=xcb build/linux-renderer/bin/firefly /absolute/path/to/main.mjs
```

The combined manifest retains the renderer's full upstream dependency graph,
Qt features, baseline and overlays, adding only the existing Mite libuv/llhttp
requirements and exact overrides. The --linux checker rejects the renderer-only,
service-only and macOS runtime manifests. A shared input reader avoids circular
imports or changing upstream files. Runtime helpers/resources use
firefly-runtime/bin and firefly-runtime/share/Lagom; macOS bundle paths are retained.
Runtime discovery first checks the dedicated tree relative to the actual native
executable (`../firefly-runtime/bin` and `../firefly-runtime/share/Lagom`), then
falls back to the configured development directory. It never chooses adjacent
upstream bin/WebContent, which lacks the runtime preload session. macOS retains
its adjacent Contents/MacOS and Contents/Resources layout. The shared production
path selector has non-GUI native filesystem tests for relocation, spaces/Unicode,
upstream decoys and missing helpers/resources. This does not establish a
self-contained Linux distributable or library/plugin closure.

The renderer workflow keeps every existing headless/window/isolation gate and
only then builds this actual application. Its dedicated Xvfb/Openbox app fixture
copies the executable and owned runtime tree to a temporary directory containing
spaces/Unicode, dereferencing development service symlinks. It runs the relocated
executable and requires the actual renderer executable to be in that relocated
tree, so fallback to the original renderer cannot pass. Native relocation
acceptance passes at `19ad113`; shared-library/plugin packaging is separate work.
The fixture serves a real HTTP document from Mite, loads a bundled ESM-authored preload,
requires a frozen document API and absent ambient Node capabilities, exchanges
validated IPC through the real bridge, checks native clipboard bytes, exercises
window sizing/centering, and verifies explicit preference/display refusals.

An independent Python HTTP peer reads /proc while the observed renderer remains
live: the actual /proc executable must be the owned runtime WebContent, with a
different PID, real parent PID, NoNewPrivs=1, Seccomp=2 and more filters than
the privileged main process. Only a successful response permits the app to exit
successfully. This proves observed sandbox activation, not complete containment.
Artifacts retain native stdout/stderr, window-manager output and kernel records.

## Reusing compiled renderer objects

The large renderer workflow opts into the [checked C/C++ compiler cache](renderer-build.md#optional-cc-compiler-cache).
Its object cache is separate from pinned vcpkg binary packages, uses the strict
owned configuration and is preserved after partial builds. It audits generated
compile commands and requires an actual cache-hit/invalidation executable gate
before the real graph. Cache statistics are evidence of reuse, not evidence of
Linux renderer behavior: all existing native DOM/compositor/process/sandbox/
preload/window tests remain required. Hosted speedups are not claimed in advance.


## ELF package closure component

[Native package helpers](../../tooling/native_package/README.md) ([ADR 0094](../architecture/0094-linux-elf-package-closure.md)) contain a
Linux x64 ELF closure stager. It resolves dependencies at original binary paths,
checks separate staged copies, deduplicates common libraries, sets relative
RUNPATHs and verifies loader resolution inside the staged lib/ tree. Host glibc
and its loader remain external requirements, recorded in the returned inventory.
No source build ELF is patched. Missing libraries, content collisions and
hardlinked/tampered staging inputs are refused.

The native CI fixture compiles real transitive shared libraries and two binary
layouts, moves the staged package and removes the original source locations
before executing them. It is a packaging component gate, not a substituted
Firefly/Designer acceptance. The actual compiled component fixture passes at
`209f64e` in [run 42348028753](https://github.com/jogibear9988/elytra/actions/runs/42348028753)
with Clang 22.1.8/patchelf 0.18.0. The experimental
[application packager](linux-packaging.md) now stages app/resources, dynamic Qt
plugins, licenses/notices, a launcher and archives. Its required native extracted-app
gate is separate and pending on that implementation. Designer acceptance and Linux
release publication remain unfinished; the component alone does not establish them.

## Portable CPU policy and native crash diagnostics

Linux renderer CI now requests the pinned upstream ENABLE_CI_BASELINE_CPU policy:
C++ -march=x86-64-v2 and Cargo -Ctarget-cpu=x86-64-v2, with Rust warnings remaining
fatal. build_renderer.py --baseline-cpu selects and audits the actual generated
C++/Cargo commands; the separate package-validation Mite SDK uses the same policy.
The Linux packager refuses SDKs without it. This replaces the renderer's previous
upstream -march=native default, which is unsuitable as a common distribution CPU
contract. It does not assert an ISA audit of every third-party instruction or
prove that CPU selection caused an observed crash.

Run 42349719779/job 128335356488 at da5e3e8 passed engine, isolation/helper and
native window gates, then its relocated app main process exited with SIGILL (-4)
before stdout/stderr. Package gates were correctly skipped. The earlier successful
8dc5830 runtime is retained as scoped evidence; the SIGILL cause is not diagnosed.
CI now records lscpu, enables bounded 512-MiB cores for actual app acceptance and,
on failure, reports registers/current-PC instructions/stack with GDB against the
original binaries. It does not rerun acceptance until green or relax kernel checks.
The baseline-policy change and new archive/Designer gates need their own native
result before being described as a verified fix or complete Linux distribution.
